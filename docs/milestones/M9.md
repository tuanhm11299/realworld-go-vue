# M9 · Hardening

**Tests:** `.specs/e2e/error-handling.spec.ts`, `.specs/e2e/xss-security.spec.ts`,
`.specs/e2e/user-fetch-errors.spec.ts`

**Goal:** make the app behave when things go wrong — which is most of what
separates a demo from software.

## Why this milestone exists

`error-handling.spec.ts` is the largest file in the upstream suite by a wide
margin. That is not an accident. The happy path is the small part of the job.

## Build

1. **Render markdown safely.** `xss-security.spec.ts` injects payloads through
   the article body, the title, the description, the bio and the profile image
   URL: `<script>`, `<img onerror>`, `<svg onload>`, `<iframe srcdoc>`,
   `javascript:` hrefs, `data:` URIs.

   Use a renderer that escapes by default, or sanitise the output (DOMPurify)
   before it reaches `v-html`. Never interpolate user input into `v-html`
   unsanitised, and be suspicious of `:src` and `:href` bound to user data —
   `javascript:alert(1)` is a valid href.

   Then ask the harder question: should the **backend** be sanitising too?
   (Defence in depth says yes for anything you will ever render elsewhere, and
   your API is public.)

2. **Fail visibly and recoverably.** Every view needs a loading state, an error
   state and an empty state. A failed fetch must not leave a spinner forever or
   render the previous page's data. `user-fetch-errors.spec.ts` will make
   `GET /api/user` fail in several ways — 401, 500, a non-JSON body, a network
   error — and check you handle each distinctly. A 401 during `restore()` means
   log out; a 500 does not.

3. **Form errors everywhere.** Every form renders `ul.error-messages` from the
   server's 422. You wrote that mapping in M7 — confirm it is used consistently
   and that a *network* failure produces a message too, not a silent no-op.

4. **Not-found routes.** Unknown URLs keep the navbar and offer a way back.

5. **Turn CI red on regressions.** Set `continue-on-error: false` on the
   `conformance` job in `.github/workflows/ci.yml`. From now on, breaking the
   suite breaks the build — which is the point of having had it all along.

## Verify

```bash
npx playwright test .specs/e2e/xss-security.spec.ts
npx playwright test .specs/e2e/error-handling.spec.ts
npx playwright test .specs/e2e/user-fetch-errors.spec.ts
make verify        # 13/13 Hurl files, 76/76 Playwright tests
                   # (63 more skip until you add the M8 seeder and switch to spa mode)
```

## Questions to answer in writing

- Which XSS payload got through first, and why did your first defence miss it?
- A 401 from any endpoint could mean the token expired. Do you log the user out
  globally, or handle it per call? What does each do to someone mid-draft in the
  editor?
- What does your app do offline? Try it: devtools → Network → Offline.
