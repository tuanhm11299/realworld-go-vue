# M6 · Comments and authorization

**Tests:** `.specs/api/hurl/comments.hurl`, `.specs/api/hurl/errors_comments.hurl`,
`.specs/api/hurl/errors_authorization.hurl`

**Goal:** finish the API, and get the difference between 401, 403 and 404
exactly right.

## Why this milestone exists

Comments are the easiest resource in the spec. The milestone is really about the
error file: an entire Hurl suite dedicated to *who is allowed to do what*. Most
real security bugs are not clever cryptography failures — they are an endpoint
that forgot to check ownership.

## Build

1. `POST /api/articles/{slug}/comments` — auth required, body required, returns
   the comment with its author as a Profile.
2. `GET /api/articles/{slug}/comments` — optional auth; each author's `following`
   flag reflects the caller.
3. `DELETE /api/articles/{slug}/comments/{id}` — author of the *comment* only.

Then walk `errors_authorization.hurl` line by line and make each case correct:

| Situation | Status |
|---|---|
| No token where one is required | `401` |
| Token present but malformed or expired | `401` |
| Valid token, but not your article or comment | `403` |
| Slug or comment id that does not exist | `404` |
| Comment id that exists but belongs to another article | `404` |

That last row is the interesting one. A comment id is globally unique, so it is
tempting to look it up and delete it. Don't — the route says which article it
belongs to, and honouring that is the difference between an API and a hole.

**This is the backend finish line.** When `make verify-api` is green, delete the
`todo` helper from `internal/handler/handler.go` — if it still compiles, you
missed an endpoint.

## Questions to answer in writing

- When should a permission failure be `404` instead of `403`? (Telling a
  stranger "that exists, you just cannot see it" leaks information. When is that
  leak acceptable?)
- Ownership checks are scattered across your handlers by now. Would they be
  better as one policy function in `internal/domain`? Try it and judge.
- Is there any endpoint where you check ownership *after* doing work that has
  already changed something?

## Going further

- Write a table-driven Go test that walks every endpoint with (no token, bad
  token, wrong user's token) and asserts the status. That test catches the next
  authorization bug before Hurl does.
