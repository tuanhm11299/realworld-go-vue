# M4 · Articles and tags

**Tests:** `.specs/api/hurl/articles.hurl`, `.specs/api/hurl/errors_articles.hurl`,
`.specs/api/hurl/tags.hurl`

**Goal:** the core resource — CRUD, slugs, tags, and the subtlest partial-update
semantics in the spec.

## Why this milestone exists

Articles bring together everything awkward: a derived identifier, a
many-to-many relationship, multi-statement writes that must be atomic, and an
update endpoint with three distinct meanings for "this field is not set".

## Build

1. **Create** — `POST /api/articles`. Required: title, description, body.
   Optional: `tagList`. Inserting the article, creating any missing tags and
   linking them is **one unit of work** — wrap it in a transaction and make sure
   a failure halfway leaves nothing behind.

2. **Slugs.** The spec only requires a unique string you can fetch, update and
   delete by. Kebab-casing the title is conventional; two articles called "Hello
   World" must still get distinct slugs. Decide how (suffix, short id, counter)
   and what happens to old links when a title changes.

3. **Read** — `GET /api/articles/{slug}` behind `MaybeAuthenticate`; `favorited`
   depends on the caller. `GET /api/articles` with combinable `tag`, `author`,
   `favorited`, `limit` (default 20) and `offset` (default 0) filters, newest
   first, returning `{"articles":[...],"articlesCount":N}` where the count is the
   **total matching the filter**, not the length of the page. List responses
   **omit the article body** (upstream changed this in 2024 for performance).

4. **Update** — `PUT /api/articles/{slug}`, author only. Someone else's article
   is `403`, not `404`. Changing the title changes the slug. And `tagList` has
   three meanings, all pinned by the suite:

   | Request | Expected |
   |---|---|
   | `tagList` absent | tags preserved |
   | `tagList: []` | all tags removed |
   | `tagList: null` | rejected |

   Same problem you solved for `PUT /api/user` in M2. Reuse that solution; if you
   cannot, that tells you it was not general enough.

5. **Delete** — author only. Comments, tag links and favourites must go too:
   `ON DELETE CASCADE`, or explicit deletes in a transaction. Know why you picked
   yours.

6. **`GET /api/tags`** — the whole tag vocabulary, no auth.

## Questions to answer in writing

- Two requests create articles with the same title at the same instant. What
  happens? If the answer is "the unique index rejects one", how does that reach
  the client — a 500, or a retry with a different suffix?
- Your list endpoint returns 20 articles. How many SQL queries did that take?
  Count them (log them, or use `pgx` tracing). If the answer is 20-something, you
  have an N+1 — leave it for now and come back in M5 having *measured* it.
- Changing a title changes the slug, so old URLs break. Is that acceptable? What
  would it cost to keep them working?

## Going further

- Add `ON CONFLICT` upserts for tags instead of select-then-insert, and reason
  about which one is safe under concurrency.
